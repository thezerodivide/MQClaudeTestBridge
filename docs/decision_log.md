### DL-003 — Guardrail mechanisms: allowlist, kill switch, watchdog, audit log

- **Status:** Confirmed, 2026-09-29 (developer's own design, recorded here per §19).
- **Requirement:** a per-test command allowlist enforced in the bridge (not just documented), including chat commands with their specific target; a kill switch (`/claudestop` in game, or `mq_halt` from Claude's side) that stops the script under test, movement, and combat, then refuses new commands until explicitly restarted; a watchdog that halts the bridge the same way if the MCP server goes quiet for a configured time; every command (allowed or refused) written to an audit log with a timestamp and the running test's name.
- **Design choices:** outside an active test run, only read-only requests are permitted at all — there is no default "general" permission mode. Commands a script under test sends on its own (e.g. autoinv's own reply tells) don't pass through the bridge's allowlist; a test that could trigger them must use fixtures/fake names that keep the side effect harmless, and the test's own proposal must say so explicitly.
- **Implementation choices:** allowlist entries checked after `${...}` expansion, with wildcard support for arguments (e.g. `/nav id *`); watchdog default timeout 5 minutes — an unmeasured first guess (Development Protocol §15), to be revisited only from actual evidence of it firing too early or too late, never adjusted preemptively.
- **Open:** none yet; will need live confirmation that the allowlist/watchdog/kill-switch mechanisms behave as designed once Phase 1's bridge exists — not yet built, so not yet testable.
- **Source:** SPEC.md "Safety and guardrails" section.

### DL-011 — Spike 2 result: what `${Lua.Script[...]}` reports on this build

- **Status:** Confirmed live, 2026-09-29, one run of `spikes/spike2_run.mac` on the developer's installed build, read from `Logs\spike2_status.txt` (recorder polling every 250 ms, logging changes) plus the MQ console as shown in the developer's screenshots. An earlier run failed because the recorder had a path-escaping fault of Claude's making (LL-001), so only the second run has recorder data.
- **Requirement:** answer spike 2: the exact values of `${Lua.Script[name].Status}`, and whether they can tell a finished script, a stopped script and a crashed script apart.
- **Design choices:** none made here. One conflict with the spec is raised in Open and needs the developer's decision.
- **Implementation choices:** none.
- **Open:** Observed: (1) `Status` returned `RUNNING`, `PAUSED` and `EXITED`. `STARTING` was never observed (a script first appeared as `RUNNING`; a 250 ms poll may simply miss it). (2) Pause and resume showed as `PAUSED` then `RUNNING` within the poll interval. (3) A script that finished by itself (PID 46), one stopped with `/lua stop` (PIDs 45, 47) and one that crashed with a Lua error (PID 48) all ended as `EXITED`. Only the finished one had return values (`ReturnCount=2`, `Return` = `function: 0x00ce4258,target-done`, meaning the first "return value" is the chunk function itself and the script's own value is item 2). The stopped and crashed scripts showed `ReturnCount=0`, indistinguishable from each other through the TLO. The `/lua` console message also ended a crash and a manual stop with the same `status -1`; a natural finish showed `status 0`. (4) No `error` status exists in the TLO on this build; the source agrees (`LuaThread.h:48`: Starting, Running, Paused, Exited). (5) A crash does print red chat lines (`... SPIKE2 deliberate error`, `stack traceback:`, function and line), which by DL-010 the bridge's catch-all event should be able to hear; not yet tested with a real listener. (6) Look-up by name returned the current run of that name once it restarted, and by PID the old entry then returned nil. The source explains it: starting a script whose name has run before erases the old entry (`MQ2Lua.cpp:590`), so there is one entry per name and no stale-entry ambiguity. A script already running is not started again (`MQ2Lua.cpp:582`): `/lua run` on a running script prints "already running" and creates no new PID, so a reload must stop it first. (7) `${Lua.PIDs}` listed running and paused scripts and dropped exited ones; it always included PID 1, a script that was already running in the developer's session (not identified). Not tested: a name that has never run, `STARTING`, behavior after a stop that has not yet completed.
- **Conflict for the developer (Protocol §1, not changed):** SPEC.md lines 84 and 101 say `lua_status` "detects crashed or finished scripts" and reports "running, finished or crashed" with the last error. Observed, `Status` cannot separate a crash from a stop. Possible sources for crash detection are the red error chat lines (spike 1 shows they reach the event matchers) or the runner's `pcall` (spike 3). Which to rely on is a design decision, not made here.
- **Supersedes:** nothing yet; the spec lines above are unchanged pending the developer's decision.
- **Source:** `Logs\spike2_status.txt`, MQ console screenshots, `references/MacroQuest Source/src/plugins/lua/MQ2Lua.cpp` and `LuaThread.h`.

**Addendum to DL-011, 2026-09-29 — crash-detection decision deferred.** The developer decided to wait until spike 3 is done before choosing how the bridge detects a crashed script, since the choice depends on whether the runner's `pcall` works. Revisit trigger: spike 3's result is recorded. SPEC.md lines 84 and 101 stay as written until then.

### DL-013 — Spike 3b result: a catch-all listener hears Lua crash text, including crashes in event and bind handlers

- **Status:** Confirmed live, 2026-09-29, on the developer's installed build. The developer ran `spikes/spike3b_run.mac` twice (the first run's console text was lost when the MQ window was resized; the listener truncates its log on start, so `Logs\spike3b_log.txt`, saved as `spikes/spike3b_log.txt`, holds the second run only). The second run's log and the developer's console screenshot agree, and the console text matches the log.
- **Requirement:** gather the evidence DL-011's deferred crash-detection decision was waiting on: can the bridge's catch-all listener (spike 1) hear a Lua error, and how does each kind of crash show up?
- **Design choices:** none made here. The decision is still the developer's (see Open).
- **Implementation choices:** none.
- **Open:** Observed: (1) A crash in a script's main chunk (`crash_main`): the listener received one chat line holding the error message, `stack traceback:` and the frames, with the line breaks removed (`...main chunk errorstack traceback:<tab>[C]: in function 'error'<tab>...`). The console shows it as several red lines; the event line arrives as one string with no separators, so parsing must not depend on newlines. The line names the script file and line number. It was followed by `Ending lua script '<name>' with PID N and status -1`, and `Status` went to `EXITED`. (2) A crash inside an `mq.event` handler and inside an `mq.bind` handler: the listener heard the same kind of line, ending with `in function <file:line>` naming the handler. In both cases the script kept running: its ticks continued to the end, it finished normally with `status 0`, and `Status` stayed `RUNNING` until it did. So handler crashes are visible only through the error text, not through status or the exit line. **Addendum to DL-021, 2026-09-29 — design item 2 approved: six-file layout for the Lua side.** Mirrors PTAutoRoute's layout: an entry script `lua/claudebridge.lua` plus modules in `lua/claudebridge/`, loaded with `require`; `/lua run claudebridge` starts it.

- `claudebridge/store.lua`: filesystem operations over an injected file-system adapter: returns a request's text or "not readable yet", writes replies, publishes the heartbeat, appends events with event numbers (criteria 6 and 7). - **Deferred, with a link:** where "completed" lives (in memory, or durably, for example by a request counting as completed when its reply exists in `outbox`) belongs with the startup and restart item and affects `queue.lua` and `loop.lua`; not decided.

**Addendum to DL-021, 2026-09-29 — design item 5 approved: a request is completed when its reply file exists in `outbox`.** The bridge keeps no separate completion state. After a restart, the highest reply number in `outbox` is the last completed request. Reply files are published by writing under a temporary name and renaming, so a half-written reply is never mistaken for a completed request (reply names are new names with no existing file, so the Windows rename-over-existing problem does not apply). This makes `loop.lua`'s invariant ("reply written before completion advances") the same event as "the reply file appears". Cost: if the bridge dies after running a request and before its reply appears, a restart would run it again. That is harmless for `ping`, `eval` and `eval_many`, which only read; for `cmd` it matters, and the "started" marker already deferred to the `cmd` slice covers it. Not decided here: what number the bridge expects first when `outbox` is empty (the MCP server's counter never goes backwards, so after a folder wipe it could start at 500 while the bridge waits for 1), and what happens to stale files at startup.

**Addendum to DL-018, 2026-09-29 — criterion 8 amended (resolves its Open item 3).** The developer approved adding the following to criterion 8, choosing to refuse when the bridge is not alive (the alternative, publishing regardless and letting the caller time out, was not chosen):

8 (added). Before publishing, `mq_eval` checks bridge liveness as defined in criterion 9. If the heartbeat is absent or older than the configured age limit, `mq_eval` returns an error stating the heartbeat's age, or that none was found. It allocates no sequence number and writes no request file.

- **Reasoning recorded with it:** a clear immediate error is easier to diagnose than a timeout, and no stale request file is left behind. Including the heartbeat age lets a caller tell a brief stall from a dead bridge. The unset age limit (criterion 6 Open 3, criterion 9 Open 1) does not block the decision. The bridge's startup floor rule (design item 6) is still needed as a backstop for the race between the check and the publish, and for files left by a crash.
- **Checked:** locally with a fake heartbeat that is absent or stale: `mq_eval` returns an error, the inbox is empty and no sequence number is used.
- **Open (new):** whether MacroQuest scripts pause during zoning or loading screens, which would make a healthy bridge look stale for a moment. Untested; it bears on how the age limit is chosen and on the wording of the error.
- **Criterion 8's Open (3) is closed by this decision.** Its other open items (timeout length, error shape, concurrent calls) stand.

**Addendum to DL-021, 2026-09-29 — design item 6 approved: bridge startup rules.** They are a backstop, since `mq_eval` refuses to publish when the bridge is not alive (criterion 8 amendment); files can still be left by a crash or by the race between the liveness check and the publish.

1. **Set the floor.** At startup the bridge notes the highest sequence number present in `inbox` and `outbox`. It never handles a request numbered at or below that floor (this is also the mechanism behind criterion 2's Assumption).
2. **First new request sets the base.** The first complete request numbered above the floor defines where strict ordering begins, with no gap check on it. From then on criterion 2's rules apply exactly. This also covers the MCP counter being far ahead of an emptied folder (criterion 3: numbers never go backwards).
3. **Log what was skipped.** Any request ignored at startup because it is at or below the floor is written to `events.jsonl`.

- **Known limitation, accepted by the developer:** if the very first request after startup is itself lost, the bridge cannot tell, because it has no earlier number to compare against; only later gaps are detected. Slice 1 is read-only, so the harm is a wasted call. If the bridge restarts mid-session, in-flight requests are treated as stale and time out, which already invalidates a run (criterion 8).
- **Not done, on purpose:** moving old files aside or cleaning folders (no criterion needs it; Protocol §3).

**Addendum to DL-021, 2026-09-29 — design item 8 approved: request, reply and error format.** Also resolves criterion 10's Open (1) (error shape) and its name-format part of Open (2). Prompted by the developer's check of the file-name width, which showed that a fixed width would eventually collide with criterion 3.

- **Sequence in the file name:** the sequence number is the file name: decimal, zero-padded to a minimum of six digits, with no upper bound (`inbox\000123.json`, and `1000000.json` after `999999.json`). It is not repeated inside the file, so the two cannot disagree. Ordering compares the numbers, never the file-name text (as text, `1000000.json` sorts before `999999.json`); a test crosses the six-to-seven digit boundary. A file whose name is not the canonical form of its number (decimal, at least six digits, zero-padded, no other leading zeros; for example `1.json`) is not a request: it is ignored and logged.
- **Requests:** `{"command":"ping"}`; `{"command":"eval","expression":"${Me.CleanName}"}`; `{"command":"eval_many","expressions":["...","..."]}`.
- **Successful replies** (`outbox\<seq>.json`): `ping`: `{"seq":N,"ok":true,"command":"ping","bridge_version":"...","character":"...","zone":"...","state":"..."}`; `eval`: `{"seq":N,"ok":true,"command":"eval","expression":"...","value":"..."}`; `eval_many`: `{"seq":N,"ok":true,"command":"eval_many","results":[{"expression":"...","value":"..."}, ...]}`, in the order requested.
- **Error replies:** `{"seq":N,"ok":false,"error":{"kind":"...","message":"..."}}` with three kinds: `unsupported_command` (a command other than the three), `invalid_request` (JSON that does not decode, or the wrong shape), `expression_too_long` (criterion 12). `kind` is what code reacts to; `message` is for humans.
- **Not decided here:** how values with control or non-UTF-8 bytes are carried (criterion 4, Open 3): `value` is a plain JSON string for now, and a second encoding may be added when that item is resolved. The exact `bridge_version` string is a build-time detail (Protocol §9).

**Addendum to DL-021, 2026-09-29 — design item 9 approved: heartbeat and event formats.** Settles criterion 6's Open (2) (character and zone when no character is in the game).

- **`heartbeat.json`:** `{"bridge_version":"...","character":"...","zone":"...","state":"running","written_at":1727612345,"waiting_for_sequence":123}`. `written_at` is whole seconds since 1970 from `os.time()`; the Python side compares it with its own clock, and both run on the same PC (one-second resolution is enough for a once-a-second heartbeat). `waiting_for_sequence` is present only during a real gap (criterion 2). `character` and `zone` are `null` when no character is in the game. `state` is only `running` in slice 1, since there is no halt yet (criterion 6's Open 1 stays open). `bridge_version` is one field beyond criterion 6's list, included so the running build is visible (Protocol §9); an implementation choice.
- **`events.jsonl`, one JSON object per line:** envelope `{"n":42,"t":1727612345,"kind":"chat","text":"..."}`. `n` is the event number (criterion 7); `t` is the time observed in whole seconds (criterion 7 left time as a design choice). In slice 1 `kind` is `chat` for every heard line, and the bridge adds three of its own for diagnostics (Protocol §8): `bridge_start` (version and floor), `request` (sequence, command and result kind for each request handled) and `startup_skipped` (a request ignored at startup by the startup rules). Crash text is recorded as an ordinary `chat` line; classifying it stays deferred.
- **Left as implementation details, on purpose:** the extra fields of the three bridge-generated kinds. Their content is as described; their field names and layout are not fixed. No criterion requires a shape, slice 1 has no tool that reads events, and fixing a schema before a reader exists would invent an interface (Protocol §3). **Revisit trigger:** when the first tool that reads events is designed.
- **Not decided here:** where event numbers start after a restart, what happens to a leftover fragment, file growth (criterion 7's Opens 2, 4 and 5), and the heartbeat replace mechanism.

**Addendum to DL-021, 2026-09-29 — design item 10 approved: the events file across restarts.** Settles criterion 7's Opens (2), (4) and (5).

1. **Append, do not truncate, and continue numbering.** At start the bridge appends to the existing `events.jsonl`, finds the last complete line's `n` and continues from `n + 1`. A cursor ("events after number 42") therefore means the same thing before and after a restart. Truncating would lose history; restarting at 1 would make cursors ambiguous.
2. **Leftover fragment.** If the file does not end with a newline (an interrupted append), the bridge writes a newline first, so its first new event starts on a fresh line. The fragment stays behind as one malformed line. Readers skip any line that is not a complete event and never treat it as one (the reader rule from criterion 7).
3. **File growth.** No rotation in slice 1. **Revisit trigger:** before the first tool that reads events is built, because reading cost depends on file size.

- **Risk noted:** the file records every chat line, so it can grow large over many sessions, and finding the last line at startup means reading from the end of the file. Accepted by the developer for slice 1, which is short-lived, until the revisit trigger.

**Addendum to DL-021, 2026-09-29 — design item 12 approved (revised): the MCP server's sequence counter is written before publishing.** The first version of this item (counter written after the rename) was withdrawn because it left a reuse hole after a crash plus a cleanup, contradicting approved criterion 3 (see LL-005).

- The counter file sits next to `inbox` and `outbox`, not inside them, so cleaning out old requests and replies does not erase it.
- One serialized step under a lock (the concurrent-calls note under criterion 3): pick the higher of the counter and the highest number in `inbox` and `outbox`, plus one; write the counter durably (Python's `os.replace`; only the MCP process reads it); then rename the finished request into `inbox` under that number.
- A failure after the counter write burns that number. It is never reused. Criterion 3 forbids reuse, not gaps; the gap is governed by criterion 2 (a missing number blocks later requests), so a burned number becomes a loud infrastructure failure: later requests time out, the run is invalid (criterion 8), and recovery is restarting the bridge, which resets its floor under the startup rules (item 6). It needs a crash or a failed rename at one specific moment, so it should be very rare.
- Rejected alternatives: counter after the rename (leaves the reuse hole after crash plus cleanup); a pending marker checked at restart (cannot tell "published, then the folders were wiped" from "never published", so it has the same hole).

**Evidence note for DL-021 design item 13, 2026-09-29 — rxi/json.lua read and tested.** The developer approved downloading the single file into a scratch folder for inspection and testing only. Downloaded from `https://raw.githubusercontent.com/rxi/json.lua/master/json.lua` (version 0.1.2 in its header, 388 lines, 9,638 bytes, MIT license header; `LICENSE` 1,048 bytes). Nothing was added to the repo. Read in full and tested with standalone LuaJIT (test files stay in the scratch folder). Observed:

- **Encode:** control bytes 0x00 to 0x1f, quote and backslash are escaped (`\u00xx` for the rest, so the `0x12` item-link byte round-trips). Byte 0x7f and every byte from 0x80 up pass through raw and unvalidated: invalid UTF-8 goes into the output as raw bytes. Numbers use `%.14g` (fine for sequence numbers and epoch seconds). An empty table encodes as `[]`. An object field set to `nil` disappears; `json.encode(nil)` gives `null`, so a `null` field can be built by assembling the object one field at a time.
- **Decode:** rejects a raw control character in a string, trailing garbage, truncated text and empty text, each with an error naming the line and column (thrown with `error()`, so `core` needs `pcall`). Accepts raw bytes 0x80 and up, decodes a lone surrogate escape into invalid UTF-8 bytes, accepts a hex number (`[0x10]` gives 16), and lets a duplicate key win last. A `null` value decodes to a missing key. Nesting of 1000 decodes; 10,000 and 100,000 give "stack overflow" (an error, not a crash). Round trips of all control bytes plus UTF-8 text, and of bytes 0x80 to 0xff, are identical within Lua.
- **Speed:** decoding is roughly quadratic in the length of a string with many escapes (string concatenation per escape): 40,000 bytes with 20,000 escapes took 0.05 s, 160,000 bytes with 80,000 escapes took 1.0 s, and a 1 MB string with about 500,000 escapes did not finish in 100 s. Encoding stayed under 0.01 s throughout. A realistic ~1 KB value with 1023 escapes took about 0.25 ms per round trip.
- **Consequences noted, none decided:** (1) criterion 4's Open (3) is real for bytes 0x80 and up (control bytes are safe): they are written raw, so a reader that decodes UTF-8 could fail or alter the value. (2) MacroQuest's Lua runs on the game's main thread, so a very large request file could freeze the client while it is decoded. Criterion 5's Open (2) left the `eval_many` list size unbounded "until there's a reason"; this is such a reason, and the request file size (or list length) may need a limit, which is a new decision. (3) `null` cannot be an object value through `nil`; the heartbeat's `null` character and zone (item 9) are built field by field, and a decoded `null` and a missing key are the same thing on the Lua side.

### DL-023 — Repository durability policy: pushes go through two gates

- **Status:** Approved, 2026-09-29, by the developer, after weighing the second reviewer's and Claude's views (both the "For Claude" reasoning and the developer's own addition). Written into `CLAUDE.md` ("Commits and pushes"). A process decision, not a design decision for the bridge.
