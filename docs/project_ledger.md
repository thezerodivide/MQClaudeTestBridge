`on_published(seq)` is called once, after successful publication, outside the lock, with the timeout origin read at the rename's return before the callback, and a callback exception changes nothing; Decision 23 (2026-10-04): the three failure cases get two new error kinds, amending item 11's list: `publish_failed` (stages `request_file`, `allocate`, `counter`, `rename`; for a `counter` failure a read-back of the counter file classifies the outcome as `not_advanced`, `advanced` (`burned_seq` is the number, advise restarting the bridge) or `unknown` (advise restarting the bridge); a `rename` failure reports `burned_seq`; `detail` is `<exception class name> errno=<n> winerror=<n>`, never the message text) and `reply_invalid` (reasons `unreadable`, `not_json`, `wrong_shape`, `count_mismatch`, `expression_mismatch`; never resent; no retry on an unreadable reply, revisit trigger the first `unreadable` reply seen live); the reply checks require `seq` to be a positive integer, not a bool or a float, equal to the outstanding number, explicit list and object type checks, exactly one of each plain and `_base64` field with plain fields ASCII-only and base64 strictly decoded, and the echoed expressions equal to those requested; an unfamiliar bridge-error kind is passed through as a reported bridge error. Counter durability is settled separately, by Decision 24 (2026-10-04): the counter file is `<bridge_dir>\sequence.counter` (decimal digits, optional trailing newline); it is written to a temporary file, flushed and `os.fsync`ed, closed, then `os.replace`d, and only then is the request published; a missing, empty or malformed counter is refused with `publish_failed` at stage `allocate` and a fixed warning (for a genuinely new installation create the file containing 0; for an existing installation do not reset it to 0), never a silent reset; criterion 3's invariant is claimed across a process crash or restart and across cleanup of the inbox and outbox, provided the valid counter is retained; OS-crash and power-loss survival are unverified and outside the guarantee, an explicit risk accepted by the developer; nothing of Step 6 is written yet. Decision 25 (2026-10-04): the request temporary file is `request-<32 lowercase hex>.tmp`, created exclusively and published with `os.rename` (never `os.replace`) to the canonical name, with owned-file cleanup; sequence numbers are decimal strings in Python (no `int()`), so `seq` and `burned_seq` in decisions 22 and 23 are strings, an explicit amendment of their wording.

## Resolved behavior

Behavior actually agreed upon (source: [SPEC.md](../SPEC.md), approved as current source of truth).

- Crash detection uses the error chat text heard by the bridge's catch-all listener; there is no wrapping runner in v1 ([DL-014](decision_log.md#dl-014--crash-detection-uses-the-error-text-the-runner-is-out-of-v1), supersedes the spec's earlier runner design). Revisit only if a real need turns up.

- Output capture is our Lua's job: MacroQuest writes no log of console or `print()` output, so the bridge, runner and `testlog` write what Claude needs to `events.jsonl` ([DL-009](decision_log.md#dl-009--output-capture-is-the-bridges-job-because-macroquest-writes-no-log)). EverQuest logs are read directly from disk.

- Two-part architecture: `claudebridge` (Lua, in MacroQuest, the only thing that touches the game) and `mq-mcp` (Python MCP server, turns bridge commands into Claude-callable tools). Claude never touches the game directly — every action goes through the MCP server and the shared folder to the bridge.
- Transport is files (an inbox/outbox folder, polled ~100ms), not sockets, for v1 — sockets are deferred to Phase 3 (multi-PC).
- A per-test command allowlist enforced in the bridge itself, not just in Claude's instructions — see [DL-003](decision_log.md#dl-003--guardrail-mechanisms-allowlist-kill-switch-watchdog-audit-log).
- Claude designs its own unhappy-path tests from reading the script under test, rather than only confirming the happy path; a standard checklist (window closed mid-run, malformed input, timeouts, repeated/spammed input, mid-run stop/restart/zone, resource exhaustion) applies to every script tested.
- Claude never fixes a bug in a script under test unprompted — it proposes testability hooks, gets approval before adding anything, and reports findings for the developer to act on. See [DL-001](decision_log.md#dl-001--retrofit-seeding-this-log-from-specmd-existing-decisions-made-section).
- Test character convention: fresh level 1, 2nd/3rd classes obtained, given platinum, moved to PoK. See [DL-004](decision_log.md#dl-004--test-character-convention).
- autoinv has exactly one gating switch (guild-only on/off); no group-only or whitelist-only mode. See [DL-005](decision_log.md#dl-005--autoinv-approval-semantics-code-is-authoritative-over-prior-descriptions).
- **Dependency policy (the developer's stated preference, 2026-10-04): outside packages are acceptable.** This is a development tool, and a user who decides they need a dependency can install it. Weigh a package on its merits in a future decision; do not reject one only because it is not in the standard library. **Nothing already decided changes automatically.** Earlier decisions that cited avoiding packages as a reason: DL-021 item 3 (`config.py` reads TOML with the standard library's `tomllib`, 'so no extra dependency'), item 4 (`unittest`, with `pytest` the alternative not chosen), item 7 (the JSON-only file transport 'is meant to avoid extra packages'), item 24 (`tools/make_test_build.py`, standard library only) and SPEC line 65 ('it needs no extra Lua packages'). Revisiting any of them would be its own decision with its own evidence. **A package is not free:** a Python dependency has to enter the pinned lock and the `--verify` machinery of DL-021 item 27 (exact names and versions, a manifest input, a new `-test.N` to change it), and a Lua dependency has to be installable inside MacroQuest's embedded Lua, as `lfs` was (decision 2). **A stale SPEC passage noticed while recording this:** SPEC line 65 says the transport needs 'no extra Lua packages', but the bridge already requires `lfs` (decision 2); to be raised as its own item under Protocol section 18, with the other stale configuration passage noted in the decision 20 addendum.

The console also showed `/lua` messages with PIDs and exit statuses (0 for a script that finished, -1 for a manual stop); these are not `${Lua.Script[name].Status}` values, so spike 2 is still open.
- Spike 2 (live, 2026-09-29, one run, [DL-011](decision_log.md#dl-011--spike-2-result-what-luascript-reports-on-this-build)): `${Lua.Script[name].Status}` gives `RUNNING`, `PAUSED` or `EXITED`. A finished script, a stopped script and a crashed script all read `EXITED`; only a finished one has return values. There is no error status. Rerunning a script erases its old entry, and `/lua run` on a running script does nothing.

A crash it catches shows in MacroQuest as a clean exit (`status 0`, no red text), so the runner must log it. Errors inside event handlers were not tested.
- Spike 3b (live, 2026-09-29, one run, [DL-013](decision_log.md#dl-013--spike-3b-result-a-catch-all-listener-hears-lua-crash-text-including-crashes-in-event-and-bind-handlers)): a catch-all listener hears a Lua crash as one chat line (message, `stack traceback:` and frames, line breaks removed) for a crash in the main chunk, an `mq.event` handler and an `mq.bind` handler. Handler crashes do not stop the script and do not change `Status` or the exit line; only the error text shows them.
- Spike 4 (local, 2026-09-29, [DL-015](decision_log.md#dl-015--spike-4-result-the-mcp-python-sdk-installs-and-works-on-python-314)): Python is 3.14.7 64-bit; `pip install mcp` gave 2.2.0 with no broken requirements, and a stdio server/client round trip worked. `mcp` 2.x renamed `FastMCP` to `MCPServer`. Not tested under Claude Code's `.mcp.json` launch.
- Spike 5 (live, 2026-09-29, one run, [DL-016](decision_log.md#dl-016--spike-5-result-a-fake-tell-fires-mqevent-so-autoinvs-tell-path-is-testable-with-one-character)): an `/echo` of a fake tell, typed-style or sent by a script with `mq.cmd` or `print()`, fires an `mq.event` using autoinv's own tell pattern with sender and body captured exactly (spaces kept), and the group-leave pattern fires the same way. autoinv's tell tests can run in Phase 1 with one character. A real tell from another player was not tested (Phase 2).
- Spike 6a (live, 2026-09-29, one run, [DL-019](decision_log.md#dl-019--spike-6a-result-mqparse-silently-truncates-its-output-at-2047-bytes)): `mq.parse` silently truncates its result to 2047 bytes (no error, no console message). A true 2047-byte value looks the same as a truncated one. Input-side behavior (test 6b) is not yet tested.
- Spike 6b (live, 2026-09-29, one run, [DL-020](decision_log.md#dl-020--spike-6b-result-a-2048-byte-input-to-mqparse-crashes-the-client)): `mq.parse` inputs of 2000, 2046 and 2047 bytes worked; an input of exactly 2048 bytes crashed the whole EverQuest client instantly (the log's last line is the "about to parse" line for 2048). 2049 and 3000 were not run. Cause is likely the fixed 2048-byte buffer copy but not confirmed. Any path that lets an expression of 2048 bytes or more reach `mq.parse` can kill the game.
- Spike 7 (local, 2026-09-29, DL-021 evidence note): with `mcp` 2.2.0, a tool that raises an ordinary exception reaches the client as the generic text "Error executing tool <name>" (the message is hidden), while a tool returning an explicit `CallToolResult(is_error=True, ..., structured_content={...})` delivers both text and structured data. Tools therefore return explicit error results carrying `kind` in the text and in `structured_content`. Whether Claude Code shows the model the structured data is not verified.
- `rxi/json.lua` 0.1.2 (read and tested 2026-09-29, DL-021 evidence notes, standalone LuaJIT): escapes control bytes but passes bytes 0x7f and above raw and unvalidated; a `nil` object field disappears and a decoded `null` becomes a missing key; decode errors embed the offending input; decode time is roughly quadratic for strings with many escapes (a 32 KiB file decodes in about 0.03 to 0.05 s at worst; 160 KB with 80,000 escapes took about 1 s); nesting deeper than roughly 8,000 to 16,000 levels fails with a catchable `stack overflow` in about a millisecond. Adopted unmodified (design item 13).
- Spike 8 (live, 2026-09-29, 32-bit client, [DL-021](decision_log.md#dl-021--phase-1-slice-1-design) evidence notes): `require('ffi')` works in MacroQuest's Lua and `ffi.arch` is `x86`. `os.rename` onto an existing file fails (`File exists`), and `os.remove` of a held-open file fails (`Permission denied`). `MoveFileExA` with `MOVEFILE_REPLACE_EXISTING` replaces a missing or unheld destination and fails safely (`GetLastError 5`, destination unchanged) when a reader holds the destination open; `GetLastError` is authoritative and `ffi.errno()` gave a stale value. No crash.
- Spike 9 (live, 2026-09-29, one run, DL-021 evidence note): a tight-loop Python reader made 185,008 reads of a test heartbeat file that the bridge-style writer replaced 6,002 times through `MoveFileExA`: 182,383 exact matches of a published generation; zero missing, invalid UTF-8, invalid JSON, inconsistent or backwards reads; 2,625 transient `PermissionError` open failures counted separately; the writer's replace was refused 3,935 times (`GetLastError 5`) under this extreme contention. Empirical evidence, not a Windows guarantee; ASCII paths only. Basis of the approved heartbeat mechanism (design item 26).
- Spike 10 (live, 2026-09-29, one 180 s run of four zone changes, DL-021 evidence notes): the largest contiguous gap in Lua execution was 9,255 ms entering The Overthere (heavy, not visited for a month); the lighter or frequently visited transitions (an empty Bazaar instance, the Bazaar with 166 players, a private Umbral Plains dynamic zone) each stalled about 3.9 to 4.3 s. After each big gap there were two further stalls of about 1.6 to 1.8 s, with the script executing between them, so they are not added to the big gap. Baseline cadence with no zoning: median 111 ms per 100 ms sample. `EverQuest.GameState` read `INGAME` throughout, including during every zone change, so it cannot detect zoning; a same-zone instance hop does not change the zone short name. Four transitions, not a worst-case bound.
- Installed MacroQuest origin (developer-confirmed 2026-09-29, from browser history and TAC's release notes): the [rel-emu-rof2 release](https://github.com/macroquest/macroquest/releases/tag/rel-emu-rof2). `references/MacroQuest Source` is that release's "Source code (zip)", unzipped by the developer (developer-confirmed), and its changelog matches the install's. Residual gap: not checked whether the release was re-published between install and source download.
- MacroQuest source review (2026-09-29, [DL-008](decision_log.md#dl-008--macroquest-source-review-print-routing-event-sources-and-logging)): Lua `print()` calls `WriteChatColorf`, which runs every plugin's `OnWriteChatColor`; the Lua plugin's handler feeds the line to every running, unpaused script's event processor. Nothing on that path writes a file. Lua errors are also written through `WriteChatColorf` (red). Output is dropped for events while `gFilterMQ` is set (`/squelch`, `/filter mq`).

## Open implementation details

Questions intentionally unresolved — do not decide these unilaterally; surface them for discussion when they become relevant. Spikes 1 to 5 are resolved and moved to Confirmed live/system facts. These are SPEC.md's "Risks and spikes," carried here so they're tracked as ledger items, not just prose in the spec.

- **How many fresh test characters are needed, and how are they reset between full-flow spellspree runs?** See [DL-004](decision_log.md#dl-004--test-character-convention).
- How the bridge recognises and parses the crash error line, and ties it to a script by file name ([DL-014](decision_log.md#dl-014--crash-detection-uses-the-error-text-the-runner-is-out-of-v1) leaves this to implementation). Untested: wording stability across MacroQuest versions, and a script that prints error-like text.
- Whether the bridge's catch-all `mq.event` keeps up at high `print()` rates, and behavior with paused or squelched output. Spike 1 itself is resolved ([DL-010](decision_log.md#dl-010--spike-1-result-a-catch-all-mqevent-hears-other-scripts-print-output)); these edge cases were not tested.
- The autoinv log path (`config\AutoInvite\autoinvite.log`) has not been checked on disk. The three log/script paths were resolved in Phase 0 ([DL-006](decision_log.md#dl-006--phase-0-log-path-verification)), and Python 3.14.7 in spike 4 ([DL-015](decision_log.md#dl-015--spike-4-result-the-mcp-python-sdk-installs-and-works-on-python-314)).
- What `core.handle` does if `env.parse` itself raises an error: no criterion covers it and it is not handled, so a raise would end the script and be read as a crash ([DL-014](decision_log.md#dl-014--crash-detection-uses-the-error-text-the-runner-is-out-of-v1)). Found in Step 3; the behavior of `mq.parse` on an unknown expression is already open (criterion 4, Open 1).
- **Possible slowness of `os.*`-style calls; the PTAutoRoute precedent (the developer's note, 2026-10-04).** In PTAutoRoute the developer moved from `os.*` commands to LuaFileSystem (`lfs`) because of how long the `os.*` commands took to complete. The same pattern has already been observed here once: `io.popen` for a directory listing took 5.4 s on its first call and 323 ms on the second against a roughly 100 ms poll (spike 11), which is why the bridge lists folders with `lfs` ([DL-022](decision_log.md#dl-022--phase-1-slice-1-build-order), decision 2); `os.execute` was not tried here. **What the bridge still uses from `os`:** `os.rename` (publishing a reply, through `fsadapter.lua`; it worked on a new name in spike 8) and `os.time` (the wall clock); the heartbeat replace goes through `MoveFileExA`, not `os`. No latency of those has been recorded. **On the Python side** the closest analogue is the `tasklist` subprocess behind `mq_status` (median 85 ms, maximum 102 ms over 60 runs, with a 5 s timeout; the alternative of calling the Windows process API through `ctypes` was considered and not chosen in DL-021 item 25). **Revisit trigger:** a stall, or latency attributable to `os.rename` (or another `os.*` or subprocess call), seen in live use or at the Step 8 live check, **or** the first time a reply is slow to appear with no other cause. **What to do then:** check whether `lfs` can do the required operation, and whether `os.rename` shows the slowness it showed in PTAutoRoute, before changing anything. **Not verified:** whether `lfs` offers a replacement for `os.rename` at all (LuaFileSystem 1.9.0 is believed not to have a rename function, which would have to be confirmed against the installed library before relying on it), and whether `os.rename` is slow in MacroQuest.
